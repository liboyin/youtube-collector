# T4: Reproducible build inputs

## Origin and boundary

From the 2026-11-07 project review of `ca869a8`. Delivered with [T3](T3.md), which holds the shared environment, validation and review.

- **Intent:** pin what the build fetches and check what it installs. The base image is pinned by tag and digest. Deno is copied from `denoland/deno:bin-2.9.8` by digest instead of the unversioned `curl | sh`. `uv lock --check --offline` runs before installation, because `uv_install.sh` at `v1.2.0` exports with `--frozen`, which never compares the lock with `pyproject.toml`. The devcontainer feature is pinned to `common-utils:2` in both configurations, each with its own committed lock.
- **Non-goals:** pinning the native Claude Code and Codex installers in the creation hook, or the `docker-build-common` tag, which is already pinned.

## Implementation

- `Dockerfile`: `COPY --from=denoland/deno:bin-2.9.8@sha256:b507583d…63543 /deno /usr/local/bin/deno` followed by `deno --version`, and `RUN UV_NO_CACHE=1 uv lock --check --offline` after copying the lock files.
- `.devcontainer/devcontainer.json` and `.devcontainer/real-data/devcontainer.json` use `common-utils:2`. `.devcontainer/devcontainer-lock.json` (previously untracked; its key changed from `:latest` to `:2`) and `.devcontainer/real-data/devcontainer-lock.json` are byte-identical, locking 2.7.1 at `sha256:e76a6a8a35d1ad824daad1540725e0ec9f8ed2dc00d2850e990a9830013c7d08`.

## Validation

- Registry, 2026-11-07: `denoland/deno:bin-2.9.8` and `bin` resolve to `sha256:b507583d3c68ba69f3ed2ce5969ae5b8b70f43421c781279c7aea06435263543`; its amd64 layer holds a single `/deno`, which reported `deno 2.9.8` in the chroot. On ghcr.io, `common-utils` tags `2`, `latest` and `2.7.1` all resolve to the locked digest.
- The offline lock check passed on the fresh lock and rejected a stale one ([T3 validation](T3.md#validation)).
- Both configurations' feature keys match their locks' keys.

## Review

Shared with T3. Round 1 found the missing real-data lock (Blocking); it was validated and fixed with the sibling lock, and round 2 confirmed the fix ([T3 review](T3.md#review)).

## Limitations

- Whether a real devcontainer build honours each lock is a host check, tracked as [T10](../TODO.md#active-backlog).
- Both locks must be kept identical by hand when the feature changes.
