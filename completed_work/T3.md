# T3: Ubuntu 26.04 and Python 3.14

## Origin and boundary

From the 2026-11-07 project review of `ca869a8`; decision C22 in [DESIGN](../DESIGN.md#11-decisions-agreed-in-discussion-2026-11-06). Delivered in one commit and one review with [T4](T4.md) and [T8](T8.md), because all three rewrite the same Dockerfile stages and T4's pinned Deno image is what lets T8 drop curl and unzip. This record holds the shared environment, validation and review.

- **Intent:** build from `ubuntu:26.04` with its distro Python 3.14, keeping the distro-Python, `ubuntu`-user (UID 1000) and `UV_PYTHON_DOWNLOADS=never` design; `.python-version` 3.14, `requires-python >=3.14`, and `uv.lock` regenerated with plain `uv lock`, keeping every package at its locked version.
- **Compatibility surface:** the `runtime` and `dev` targets and the Compose wiring keep their names; the venv stays at `/opt/venv`, its interpreter becomes `/usr/bin/python3.14`. No HTTP contract or application layout exists yet.
- **Non-goals:** dependency changes (T6), tool configuration (T7), application code, entrypoint and port.
- **Validation and done criteria:** a simulated build, the gates under Python 3.14, review without unresolved Blocking findings.

## Implementation

`Dockerfile` starts from `ubuntu:26.04@sha256:6a06111c…f4d3c`; `.python-version` and `pyproject.toml` move to 3.14; `uv.lock` was regenerated. README and DESIGN section 7 describe the result.

## Validation

Environment: this repository's devcontainer (Python 3.12.3, no Docker daemon), 2026-11-07. Docker builds being impossible here, the stages ran in a chroot of the real image instead:

- Registry: `ubuntu:26.04` and `ubuntu:resolute` both resolve to index `sha256:6a06111c3b0a8600feadb270aec771dc239bf407b25625f93f44ab00e11f4d3c`. The two amd64 layers downloaded matched their digests. The rootfs is Ubuntu 26.04.1 LTS, with `ubuntu:x:1000:1000` in `/etc/passwd`.
- The chroot used the `docker-build-common` `v1.2.0` helpers, uv 0.13.7 and Deno from the pinned image layer, and gave Python 3.14.4, ffmpeg 8.0.1 and git 2.53.0. `/proc` could not be mounted; device nodes were created instead.
- Lock: `uv lock` under Python 3.14.4 kept the same 87 package names and versions. Only `requires-python`, the resolution markers and the cp312/cp313 wheels changed; the reviewer confirmed that the removed wheels and markers apply only below Python 3.14.
- Build steps ran as UID 1000: the offline lock check, the dependency install, then the project install. With the working directory at `/`, the venv imported `youtube_collector` from site-packages, and yt-dlp 2026.10.26 ran.
- Gates on the final candidate inside the chroot, under Python 3.14.4: `uv lock --check --offline`, `./check-coverage.sh` (55 tests, 100% statement and branch), `mypy youtube_collector` (mypy 2.4.1) and `ruff check .` (ruff 0.17.4) passed, and passed again after the review fix. Compose renders were unchanged from [T2](T2.md#validation).
- Baseline: the gates passed at `83cb7b9` in this container under Python 3.12.3.

## Mutation evidence

No application invariant changed. Behavioral probes stood in for mutants: a `pyproject.toml` edit that left the lock stale made the build's offline lock check fail (main agent and reviewer, independently), and the reviewer confirmed that the runtime venv still imports after the source tree, git, uv, curl and unzip are removed.

## Review

Codex `gpt-6.1-sol`, medium effort (dispatch arguments), thread `01a1b3f3-afe9-7541-8394-ea7b3833c79d`, shared with T4 and T8. Integrity snapshots matched around both rounds.

- **Round 1, Finding 1 (Blocking), Validated, fixed:** the Dev Containers CLI reads the feature lock next to the selected configuration (`getLockfilePath` in `devcontainers/cli` `src/spec-configuration/lockfile.ts`), so the real-data configuration would ignore the parent lock and resolve the mutable `common-utils:2`. Fix: `.devcontainer/real-data/devcontainer-lock.json`, byte-identical to the default lock. Recorded under [T4](T4.md).
- **Round 2:** finding resolved, no new findings. Verdict: no blocking findings.

## Limitations

- No real Docker build: BuildKit's bind mounts from the named context, the ownership `COPY --from` produces, layer caching, devcontainer creation on the new image and arm64 are unverified. They are tracked as [T10](../TODO.md#active-backlog).
- The chroot used uv from this container, the same 0.13.7 release the image pins by digest, rather than a binary copied from that digest.
- Working evidence lived in session scratch storage and is not retained beyond this record.
