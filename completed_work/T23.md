# T23: Change feed and long-poll wake-ups

## Origin and boundary

Planned by [T9](T9.md), and unblocked by decision C38, which settled DESIGN Q3 (the user chose latest-state pages, two snapshots, and undetected cursors from another database). The accepted boundary, as it stood in TODO:

- **Intent:** DESIGN 5.10 with C27 and C38: change pages with cursors, 410 below the pruned-through revision, snapshot revisions for resynchronization, and wake-ups for waiting requests.
- **Implementation direction:**
  - In `youtube_collector/store.py`:
    - `changes(since, limit)` reads, in one transaction, the pruned-through revision and every job, item and failure row with `revision > since`, ordered by revision, up to `limit`. It returns a `ChangePage` of entries (`kind`, `id`, `revision`, `removed`, `record`; job records carry no items), the next cursor (the last revision on the page, or `since` when empty) and `more`. It raises `CursorPruned` when `since` is below the pruned-through revision (C27).
    - `jobs_snapshot()` and `failures_snapshot()` return the status table or the uncleared failures with the revision they were read at, from one read transaction (C38).
    - `job_view(job_id)` returns a live job with its items and its view revision: the highest revision among the job and its items, removed ones included, so an item's removal counts as a change to the job.
  - `youtube_collector/notify.py`, `Notifier`:
    - `bind(loop)` attaches the event loop. `notify()` may be called from any thread, and is a no-op before binding and after the loop closes; waiters always reread the database, so a lost early notification loses nothing.
    - `ticket()` returns the current wake-up event and `wait(ticket, timeout)` awaits it. Taking the ticket before reading the database means a change committed between the read and the wait still wakes the waiter.
    - `long_poll(read, ready, timeout)` repeats ticket, read and wait until `ready(result)` holds or the timeout passes, then returns the last result. It runs on an injected monotonic clock.
- **Compatibility surface:** the change-entry shape and cursor semantics that T24 serves, and the snapshot revisions of `GET /jobs` and `GET /failures`.
- **Non-goals:** HTTP parameters, the `wait` cap, status codes and response models (T24); running database reads off the event loop (T24 chooses).
- **Validation:** store tests on a temporary database: order and coalescing (a record appears once, at its latest revision, and moves forward when it changes again), tombstones in pages, the limit and `more`, cursor continuity across pages, the pruned-through boundary (`since == P` accepted, `since < P` rejected), snapshot revisions, and job views counting item removals. Notifier tests on a real event loop: notification from another thread, before binding and after close; no lost wake-up between ticket and wait; and `long_poll` returning at once on changes, after a wake-up, and on timeout.
- **Mutation evidence:** for the cursor boundary, ordering and coalescing, the ticket-before-read ordering, and `notify` from other threads.
- **Done:** gates, review and a completion record.

## Implementation

- **`youtube_collector/store.py`** gains `ChangePage`, `Snapshot`, `JobView`, `CursorPruned`, `changes`, `jobs_snapshot`, `failures_snapshot`, `job_view` and `_read_meta`. `changes` queries each table for up to `limit + 1` rows above `since`, merges them by revision and keeps `limit`. The extra row decides `more` without a count query.
- **`youtube_collector/notify.py`:** `Notifier`.
- **DESIGN section 14** lists `notify` and the store's feed reads.
- **Tests:** `tests/test_store.py` gains 13 feed tests (83 in all). `tests/test_notify.py` has 12 tests, which run on fresh event loops through `asyncio.run`.

## Validation

## Mutation evidence

The main agent was the primary producer, with the same isolation, command and provenance check as [T15](T15.md#mutation-evidence), on `tests/test_store.py` and `tests/test_notify.py` (baseline 95 passed). A session-end hook found no thread still alive in any run.

- **M1, a cursor equal to P rejected:** five feed tests failed.
- **M2, cursors below P accepted:** the 410 test failed.
- **M3, entries not merged by revision:** the tombstone and cross-kind merge tests failed.
- **M4, the cursor jumps to the highest revision fetched:** the paging and merge tests failed.
- **M5, `more` off by one:** it first survived. An exactly full page assertion was added, and then the paging test failed.
- **M6, the job view ignores items:** `job_view_counts_item_changes_and_removals` failed.
- **M7, the snapshot revision replaced:** the jobs snapshot test failed.
- **M8, the ticket taken after the read:** `long_poll_takes_its_ticket_before_reading` failed. It is deterministic: the read lets the wake-up run before it returns.
- **M9, a wake-up that is not thread-safe:** it first survived twice. The thread could notify before the waiter blocked, and then the loop woke on an outer timeout. Now the thread waits until the coroutine is about to block, pauses a bounded 0.2 s, and the test asserts the wake-up latency is under 5 s against a 10 s timeout. The mutant took about 10 s and failed.
- **M10, the old ticket kept after a wake-up:** `each_notification_starts_a_fresh_ticket` failed.

## Review

Codex `gpt-6.1-sol`, medium effort (dispatch arguments), thread `01a1b843-e712-7500-82a1-2d38b2206577`. The reviewer replayed M1–M10 with verified scratch imports and ran four extra cases, which passed (seed 2307):

- concurrent commits during both snapshot reads;
- cancellation with shared waiters;
- a real long-poll timeout.

M7 replaces the revision rather than moving the read outside the transaction, so the reviewer added mutants that do move it, for both snapshot methods; its concurrent-commit probes killed both. Integrity snapshots matched. Verdict: no blocking findings, no Non-blocking findings or Nits.

## Limitations

- The reviewer's transaction-boundary probes are not in the repository's suite. The repository's own M7 guards the revision value, not the transaction boundary.
- Wake-up latency is asserted against wall time, with a bounded 0.2 s pause and a 5 s limit. It is a negative check, as described.
