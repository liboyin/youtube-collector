# T22: Reconciliation thread

## Origin and boundary

Planned by [T9](T9.md). The accepted boundary, as it stood in TODO:

- **Intent:** DESIGN 5.8, 5.13 and 5.14's staging result, with C25, C26 and C35: keep the status table in step with staging without the API ever touching the share.
- **Implementation direction:** `youtube_collector/reconcile.py`, class `Reconciler`.
  - `run()` opens the thread's own store and runs a pass at once, then every `interval` (default 30 s) or on request, until `stop()`.
  - `run_pass(store)`:
    - It checks the marker, and returns with no record change and no file probed while the marker is missing.
    - It probes each done or failed item's recorded files with `staging.file_present`. An item whose files are all gone is removed, including items that recorded none; an item whose check raises is kept.
    - It checks the marker again before any write, so a share lost part-way changes nothing, because an unmounted share looks empty.
    - It then removes the items, removes finished jobs with nothing left (C26), and prunes tombstones older than `tombstone_retention` (default 7 days). It notifies when anything changed.
  - The API calls `request_pass()`, `wait_for_pass(ticket, timeout)`, `last_reconciled_at()` and `staging_check()`. None of them touches the share, and the lock is never held while probing, so they stay responsive during an SMB stall (C25).
    - A ticket is satisfied only by a pass that started after the request. Requests made while a pass is pending share it, so at most one probe is outstanding.
    - `staging_check()` returns the last marker result with its monotonic time, from which T24 derives its age. The age threshold for unhealthy is T24's implementation default (C35).
  - A failing pass is logged, releases its waiters, and the loop continues.
- **Decision within DESIGN's latitude (assumption):** "files it produced or found existing" means the paths the item recorded, so a file the user renamed in staging no longer keeps its record. Matching by ID instead would also count files that `youtube-whisperer` writes beside the media (DESIGN 5.8 excludes those).
- **Compatibility surface:** which records `GET /jobs` lists and when tombstones appear in the change feed (T23, T24); the tombstone retention setting.
- **Non-goals:** HTTP handling and the waiting budget of `GET /jobs` (T24); the change-feed reads (T23); the worker's own marker check (T21).
- **Validation:** tests with a real store and staging root under `tmp_path`. They cover:
  - removal rules: any recorded file present keeps an item, no files removes it, and live items and their jobs stay;
  - no change and no probe while the marker is missing, and no change when the share disappears mid-pass;
  - unreadable files kept, pruning, and notification only on change;
  - ticket semantics before and during a pass;
  - API calls finishing within a bound while a probe is blocked;
  - the thread's start, request and stop, and a failing pass releasing its waiters.
- **Mutation evidence:** for both marker checks, the removal rule, unreadable files, ticket semantics, the waiter release, the lock not being held while probing, and notification.
- **Done:** gates, review and a completion record.

## Implementation

`youtube_collector/reconcile.py`: `Reconciler`, `StagingCheck` and `PassResult`.

- One `threading.Condition` guards the pass counters (started and completed), the time of the last reconciliation and the cached marker check. It is never held during a filesystem call.
- The three writes run in a `try` whose `finally` notifies when any of them committed a change.
- DESIGN section 14 lists the module.
- `tests/test_reconcile.py` has 13 tests, which use a real store and staging root under `tmp_path`. Failure injection replaces `testee.staging` with a namespace of the real functions, some overridden.

## Mutation evidence

The main agent was the primary producer, with the same isolation, command and provenance check as [T15](T15.md#mutation-evidence), on `tests/test_reconcile.py`. A scratch-only session-end hook listed the non-main threads still alive; there were none in any run.

- **M1, no marker check after probing:** `changes_nothing_when_the_share_disappears_mid_pass` failed.
- **M2, no marker check before probing:** `changes_nothing_while_the_marker_is_missing` (files were probed while paused) and the stalled-probe test failed.
- **M3, unreadable files count as gone:** `keeps_items_whose_files_cannot_be_checked` failed.
- **M4, an item is kept only while all its files remain:** `removes_items_whose_files_are_gone_and_their_jobs` failed.
- **M5, a running pass satisfies later requests:** both `request_pass` tests failed.
- **M6, a failed pass does not release its waiters:** `run_survives_a_failing_pass_and_releases_waiters` failed.
- **M7, the lock held while probing:** `a_stalled_probe_does_not_block_api_reads` failed its bounded five-second completion check.
- **M8, removals without notification:** the removal test failed.
- **M9, notification only after every write succeeds (the reviewed defect):** `notifies_committed_removals_when_a_later_write_fails` failed.

Assertions added after the first batch only add protection. M2, M8 and M9 were run on the final tests.

## Review

Codex `gpt-6.1-sol`, medium effort (dispatch arguments), thread `01a1b6ad-c272-7823-846e-06a4a6e9c0cf`.

- **First assessment: one Blocking finding.** The three writes commit separately, but notification ran only after all three, so a failure in `prune` after committed removals left long-poll waiters unaware. The reviewer reproduced it with a second SQLite writer holding the lock; it was validated and fixed.
- **Follow-up:** resolved, and the reviewer's contention reproduction passes. Verdict: no blocking findings and no new findings.

Integrity snapshots matched after both assessments.

## Limitations

- An SMB stall is simulated by a probe blocked on an event. Real blocked metadata calls on the user's share are unverified.
- Reconciliation follows recorded paths, the boundary's assumption, so a file renamed in staging no longer keeps its item.
