# T19: SQLite store

## Origin and boundary

Planned by [T9](T9.md). The accepted boundary, as it stood in TODO:

- **Intent:** the status table, failures, idempotency keys and revisions of DESIGN 5.1, 5.3, 5.7–5.10 and 5.12, stored as section 7 and C36 require, so that every later component reads and writes through one module.
- **Implementation direction:** `youtube_collector/store.py`.
  - `initialize(path)` creates the schema once at startup (`PRAGMA user_version` 1; an unknown version raises) and enables WAL. `Store(path, clock)` owns one connection and is used only by the thread that opened it (sqlite3's own thread check stays on), with a busy timeout. Every write is one `BEGIN IMMEDIATE` transaction; every multi-statement read is one transaction, so it sees one snapshot.
  - One global revision counter in a `meta` table. Every record a write changes, including its removal, takes the next revision, in statement order, so a record's row always carries its latest revision. Removal sets `removed_at` and leaves the row as a tombstone holding its final state. This makes DESIGN Q3's proposal a plain query (T23) without precluding the alternatives.
  - Jobs carry a submission sequence, kind, submitted URL, target type and ID, languages, state and playlist title. A single-video job gets its one item at submission; a playlist job gets its items when expansion completes, in one transaction that also moves the job to `running` (DESIGN 5.3). Items carry position, video ID, title, state, per-artifact outcome and staging-relative path, the caption track's code and kind, and progress bytes.
  - Worker writes: start and complete or fail expansion, start an item, record progress, and finish an item together with its new failures and their supersession, finishing the job once no item is queued or running. A job whose expansion fails becomes `finished` with its failure (DESIGN 5.7).
  - `next_work(after_seq)` returns the next job, in submission order after `after_seq` and wrapping around, that needs expansion or has a queued item, with that item; the worker keeps the cursor, which makes the scheduling round-robin (C9).
  - Supersession (DESIGN 5.9): finishing an item with a definitive media outcome (`downloaded`, `existing`) removes uncleared failures for the same video whose artifact is media, and likewise for captions (`downloaded`, `existing`, `unavailable`); completing an expansion removes uncleared expansion failures for the same playlist. Removal by supersession or by clearing leaves a failure tombstone.
  - Reconciliation writes: remove given done or failed items, and remove every `finished` job with no live items and no uncleared failure referring to it (C26). Removing a job turns its idempotency key's record into the job's final representation with an expiry (C24, C34).
  - Submission with an idempotency key, in one transaction: the same key and body returns the existing job (live, or its stored final representation after removal) and reports that nothing was created; the same key with a different body raises a conflict; an expired key is forgotten. The caller supplies the canonical body.
  - `prune(retention)` deletes tombstones older than the retention and expired keys, and raises the durable pruned-through revision to the highest revision pruned (C27).
  - `recover()` at startup returns `running` items to `queued` and `expanding` jobs to `queued` (DESIGN 5.12), each change taking a revision.
  - Records convert to plain JSON-ready dictionaries, the shape responses and stored final representations share; timestamps are ISO 8601 UTC strings.
- **Assumption (DESIGN 5.9 names no artifact for `metadata`-phase failures):** a metadata failure belongs to media when the job requests media and to captions otherwise, so a later definitive result for that artifact supersedes it. Effect: a `videos` metadata failure clears once the media later downloads; it does not clear on a later captions-only success.
- **Compatibility surface:** the database file's schema, versioned by `user_version`, and the dictionary shapes that T23 and T24 will serve. No HTTP contract exists yet.
- **Non-goals:** change-feed reads and long-poll notification (T23); filesystem checks (T22); HTTP status codes and request validation (T24).
- **Validation:** tests against a SQLite file under `tmp_path` with an injected clock: strictly increasing revisions per change, including removal and progress; one-transaction writes leaving no partial state when a statement fails; round-robin `next_work` with wrap-around; supersession for each artifact and for expansion, never touching other videos, artifacts or playlists; reconciliation removal rules; key replay before and after removal, conflict, and expiry; pruning boundaries and the pruned-through revision; recovery; the schema version check; and a connection refusing use from another thread. Mutation evidence for revision assignment, supersession scope, the job-removal conditions, key conflict detection and the pruned-through revision.
- **Done:** gates, review and a completion record.

## Implementation

`youtube_collector/store.py` holds `initialize`, the `Store` class, the state and outcome enums, the input dataclasses (`NewFailure`, `PlaylistEntry`, `ItemResult`), the worker's `WorkUnit`, reconciliation's `ItemFiles` and the `Submission` result. Design points:

- Connections use `autocommit=True` (Python 3.12+), with explicit `BEGIN IMMEDIATE` for writes and `BEGIN` for multi-statement reads.
- Tables are `STRICT`. Job and failure order uses `AUTOINCREMENT` sequences, so pruning never reuses a number.
- `revision` is `UNIQUE` per table and comes from one counter in `meta`. Because `BEGIN IMMEDIATE` serializes writers, revisions become visible in commit order, with no gap a reader could skip.
- Representations are plain dictionaries: a job has `target`, `languages`, `state`, `playlist_title`, timestamps, `revision`, `removed` and `items`. An item has `media` or `captions` only when its kind requests them, and `progress` with bytes and a percentage. A failure carries `removal` (`cleared` or `superseded`) once removed.

`tests/test_store.py` has 70 tests, each on its own database file under `tmp_path`, with an injected clock.

## Limitations

- Concurrency was exercised with separate connections in one thread and the cross-thread check. Multi-threaded contention is covered by SQLite's locking and the 30-second busy timeout, not by a stress test.
- The supersession of metadata-phase failures follows the boundary's recorded assumption, because DESIGN 5.9 does not name their artifact.
