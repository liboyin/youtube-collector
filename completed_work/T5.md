# T5: SSH agent forwarding

## Origin and boundary

From the 2026-11-07 project review of `ca869a8`; decision C31 in [DESIGN](../DESIGN.md#11-decisions-agreed-in-discussion-2026-11-06). Delivered in one commit and one review with [T2](T2.md); that record holds the shared environment, gates and review.

- **Intent:** remove the `~/.ssh` bind mount from both devcontainer configurations, so private key files are not present in a full-access agent container; Git over SSH uses the agent VS Code forwards.
- **Retained behavior:** the mount also supplied `known_hosts`, and the remote is `git@github.com:...`. Its owner is now the creation hook, which writes GitHub's SSH host keys fetched over verified HTTPS from `api.github.com/meta` into `~/.ssh/known_hosts` (directory mode 700) and fails creation if the fetch fails or lists no keys. Other hosts get no preloaded key.
- **Non-goals:** changing the `.gitconfig` mount, commit signing, or the host's agent setup.
- **Validation and done criteria:** isolated runs of the host-key step, the shared T2 checks, review without unresolved Blocking findings.

## Implementation

`.devcontainer/devcontainer.json` and `.devcontainer/real-data/devcontainer.json` mount only `.gitconfig` and the workspace; `.devcontainer/postCreateCommand.sh` gains the host-key step; README tells the user to load the key into the host's agent and check `ssh-add -l` inside the container.

## Validation

- `bash -n` on the hook. The host-key step, extracted and run under a scratch `HOME`, wrote three `github.com` entries into a mode-700 directory, and the live ed25519 key that `ssh-keyscan` returned matched one of them; against an unreachable endpoint it exited 1.
- The reviewer also ran the exact block with curl doubles: empty key lists and malformed JSON failed closed as well.
- At the time of the change this container had no forwarded agent (`SSH_AUTH_SOCK` unset); Git over SSH had relied on the mounted key file.

## Mutation evidence

Reviewer-produced, in the batch described in the [T2 record](T2.md#mutation-evidence): restoring the `~/.ssh` mount in the default configuration, and separately in the real-data configuration, each failed the no-SSH-mount assertion.

## Review

Shared with T2: thread `01a1b3eb-1511-7862-8024-d21f245ad75d`; no findings.

## Host checks

Run on 2026-11-07 at `e7dbe4b` inside the rebuilt default devcontainer (Ubuntu 26.04.1 LTS, Python 3.14.4), by Claude Code 2.1.319 from the VS Code extension; part of [T10](../TODO.md#active-backlog).

- `ssh-add -l`: failed, "Could not open a connection to your authentication agent". `SSH_AUTH_SOCK` is unset and no forwarded agent socket exists anywhere in the container.
- `git fetch --dry-run` over SSH: failed (exit 128, no access), consistent with the missing agent.
- Likely cause, unverified: the host had no running agent holding the key when VS Code attached, which the limitation below anticipates. Not yet ruled out: whether a VS Code integrated terminal receives a socket that the Claude Code extension process does not.

Host run on 2026-11-07 at `bf7dc39` by the user, with the default devcontainer running (WSL2 kernel 6.6.87.2, Docker 29.6.2), using an untracked one-off script (`t10-host-checks.sh`):

- Host `ssh-add -l`: failed, "Could not open a connection to your authentication agent". The user's WSL shell reaches no SSH agent, so VS Code most likely had none to forward, which would explain the in-container failure above. Agent setup on the host is the user's step; the check is repeated after it.

Rerun on 2026-11-07 at `f3a25e3` after the user set up a WSL agent at a fixed socket path, loaded from `~/.profile` and VS Code's `~/.vscode-server/server-env-setup`, restarted WSL and reopened the devcontainer:

- In a VS Code integrated terminal (reported by the user) and in the Claude Code extension's own process: passed. Both see the same forwarded `SSH_AUTH_SOCK=/tmp/vscode-ssh-auth-<uuid>.sock`, `ssh-add -l` lists the user's 4096-bit RSA key, and `git fetch --dry-run` over SSH exits 0. The terminal and the extension process receive the same socket, so the question left open in the first run is closed.
- This confirms that the earlier failures came from the missing host agent, not from the devcontainer configuration.

## Limitations

- Forwarding needs an agent on the host that holds the key when VS Code's WSL server starts; without one, Git over SSH from the container fails, as the first two runs above show. The host setup lives outside the repository and is not covered by any automated check.
