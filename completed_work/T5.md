# T5: SSH agent forwarding

## Origin and boundary

From the 2026-11-07 project review of `ca869a8`; decision C31 in [DESIGN](../DESIGN.md#11-decisions-agreed-in-discussion-2026-11-06). Delivered in one commit and one review with [T2](T2.md); that record holds the shared environment, gates and review.

- **Intent:** remove the `~/.ssh` bind mount from both devcontainer configurations, so private key files are not present in a full-access agent container; Git over SSH uses the agent VS Code forwards.
- **Retained behavior:** the mount also supplied `known_hosts`, and the remote is `git@github.com:...`. Its owner is now the creation hook, which writes GitHub's SSH host keys fetched over verified HTTPS from `api.github.com/meta` into `~/.ssh/known_hosts` (directory mode 700) and fails creation if the fetch fails or lists no keys. Other hosts get no preloaded key.
- **Non-goals:** changing the `.gitconfig` mount, commit signing, or the host's agent setup.
- **Validation and done criteria:** isolated runs of the host-key step, the shared T2 checks, review without unresolved Blocking findings.

## Implementation

`.devcontainer/devcontainer.json` and `.devcontainer/real-data/devcontainer.json` mount only `.gitconfig` and the workspace; `.devcontainer/postCreateCommand.sh` gains the host-key step; README tells the user to load the key into the host's agent and check `ssh-add -l` inside the container.

## Validation

- `bash -n` on the hook. The host-key step, extracted and run under a scratch `HOME`, wrote three `github.com` entries into a mode-700 directory, and the live ed25519 key that `ssh-keyscan` returned matched one of them; against an unreachable endpoint it exited 1.
- The reviewer also ran the exact block with curl doubles: empty key lists and malformed JSON failed closed as well.
- At the time of the change this container had no forwarded agent (`SSH_AUTH_SOCK` unset); Git over SSH had relied on the mounted key file.

## Mutation evidence

Reviewer-produced, in the batch described in the [T2 record](T2.md#mutation-evidence): restoring the `~/.ssh` mount in the default configuration, and separately in the real-data configuration, each failed the no-SSH-mount assertion.

## Review

Shared with T2: thread `01a1b3eb-1511-7862-8024-d21f245ad75d`; no findings.

## Limitations

- Agent forwarding and a real Git fetch inside a rebuilt container are unverified, tracked as [T10](../TODO.md#active-backlog). Until the user's host agent holds the key, Git over SSH from the new container fails.
