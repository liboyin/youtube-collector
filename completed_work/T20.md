# T20: Acquisition adapters

## Origin and boundary

Planned by [T9](T9.md). The accepted boundary, as it stood in TODO:

- **Intent:** DESIGN 5.3 (expansion), 5.5 (media), 5.6 (caption listing and SRT), 5.10 (progress values) and 5.11 (cookies), with D38's timeouts: thin adapters around yt-dlp and `youtube-transcript-api` that report facts and raise library errors unchanged, so the worker (T21) decides outcomes and categories.
- **Implementation direction:**
  - `youtube_collector/youtube.py`: `YoutubeClient(cookies, pacing, factory)`, where `factory` builds a `yt_dlp.YoutubeDL` (a `Downloader` protocol for tests).
    - Every request shares quiet options with output routed to logging, `js_runtimes={'deno': {}}` stated explicitly, the configured pacing (`sleep_interval_requests`, `sleep_interval`, `max_sleep_interval`; `Pacing` defaults to none), and `cookiesfrombrowser=('firefox',)` when cookies were detected.
    - `expand_playlist(url)` uses `extract_flat='in_playlist'` and skips empty or ID-less entries.
    - `video_info(url)` extracts once with `process=False`, so no format is selected and a `captions` job never fails on media formats.
    - `download_media(video, path, on_progress)` hands that same extraction to `process_ie_result` with the source revision's format, `merge_output_format='mp4'` and a literal output template (`%` escaped). A download therefore costs no second extraction, one request at a time (DESIGN 5.3).
    - Progress accumulates bytes across the video and audio files. The total is the known size so far, and None while the current file's size is unknown.
    - `firefox_profile_roots(home)` and `firefox_cookies_present(roots)` detect a `cookies.sqlite` by name in yt-dlp's Linux locations, including the snap path Compose mounts, without opening it.
  - `youtube_collector/captions.py`: `CaptionClient(api)` with `find_track(video_id, languages)` and `fetch_srt(track)`.
    - `find_track` returns the T16 selection from the listed tracks only, or None when captions are disabled or nothing matches; other caption-service and `requests` errors propagate.
    - `fetch_srt` formats with `SRTFormatter`.
    - The default API uses a session whose HTTP adapter applies a `(10, 30)` second timeout to requests without one.
  - `pyproject.toml` and README Testing gain the `yt_dlp` mypy override.
- **Revalidated:** the compact entry's dependency on T17 is not needed: publication stays in the worker, which writes through T17. `youtube.py` does not import the store; the worker converts `PlaylistVideo` to the store's entries.
- **Compatibility surface:** the yt-dlp options and the caption request timeouts, which determine YouTube traffic. No HTTP contract, setting or on-disk layout changes; the pacing values become settings in T24.
- **Non-goals:** deciding outcomes, categorizing errors, publication and throttling (T21); detecting cookies once per process (T24 calls the detection); cookie authentication for captions, which `youtube-transcript-api` 1.2.5 has disabled.
- **Validation:** fakes for `YoutubeDL` and the transcript API assert options, calls and error propagation. The real `YoutubeDL` accepts the options without network access. An offline test runs real yt-dlp on an unprocessed extraction whose formats a test-owned loopback HTTP server serves, proving format selection, the literal path with template characters and the progress values. A real `requests.Session` reaches the adapter with the default timeouts. Cookie detection runs only on test-owned directories. No mutation evidence is required unless review asks: the adapters decide no outcomes.
- **Done:** gates, review and a completion record.

## Implementation

- `youtube_collector/youtube.py`: `YoutubeClient`, `Pacing`, `Playlist`, `PlaylistVideo`, `VideoInfo`, the `Downloader` protocol, `firefox_profile_roots` and `firefox_cookies_present`.
- `youtube_collector/captions.py`: `CaptionClient` and `timeout_session`, whose `HTTPAdapter` subclass fills in the default timeout.
- `pyproject.toml`: the mypy override covers `yt_dlp.*`; README Testing says so.
- DESIGN section 14 lists both modules.
- Tests: `tests/test_youtube.py` (30) and `tests/test_captions.py` (12).

## Validation

Environment: the devcontainer, Python 3.14.4, yt-dlp 2026.10.26, youtube-transcript-api 1.2.5, 2026-11-07. Baseline: the gates passed on T19's candidate ([T19](T19.md#validation)); `35627f4` adds only DESIGN prose.

The final candidate ran in a git worktree of `35627f4`, with `PYTHONPATH` set to the worktree and the import checked to resolve there: `./check-coverage.sh` passed (450 tests; both adapters 100% statement and branch), and mypy and Ruff passed.

Empirical library checks, all offline:

- The real `YoutubeDL` accepts the options; yt-dlp validates `js_runtimes` itself.
- Real yt-dlp processes an extraction that skipped processing, through `process_ie_result`. It chose the MP4 format over a WebM one, wrote exactly to a literal path containing `%(title)s` and `100%`, left nothing else in the stage directory, and reported `(4096, 4096)`. The formats were served by a test-owned server on 127.0.0.1.
- A real `requests.Session.get` without a timeout reaches the adapter with `(10.0, 30.0)`.
- A first version of the offline test used `file://` formats. yt-dlp's file handler leaks its own file handles, and pytest reported them as unraisable warnings in random tests, so the test was rebuilt on the loopback server.

## Mutation evidence

The boundary required none for the adapters, which decide no outcomes. The review's fix has one mutant, run with the same isolation, command and provenance check as [T15](T15.md#mutation-evidence), on `tests/test_youtube.py`, plus a scratch-only session-end hook listing the non-main threads still alive.

- **T20-M1, the loopback server's handler threads are daemon again** (`daemon_threads = True`): `test_loopback_server_close_waits_for_request_handlers` failed. No thread was alive at session end, in the baseline (30 passed) or under the mutant.

## Review

Codex `gpt-6.1-sol`, medium effort (dispatch arguments), on the worktree's dirty tree; four assessments in one thread.

- **First assessment:** the reviewer ran the 41 adapter tests then present (seed 20420). Its event-controlled probe found **Blocking finding 1**: the loopback fixture used `ThreadingHTTPServer`, whose handlers run on daemon threads that `server_close` does not join, so a handler could outlive its test-owned directory. Validated against Python 3.14's `socketserver`. Fixed with a `LoopbackServer` subclass (`daemon_threads = False`) and a regression test.
- **Follow-up 1:** finding 1 resolved. **Blocking finding 2:** the regression test's cleanup ran only on success, so under the mutant it left its threads running. Fixed with unconditional teardown.
- **Follow-up 2:** finding 2 partly resolved. Under the mutant, the handler ran on an untracked daemon thread. Fixed by recording each handler thread and joining it in teardown.
- **Follow-up 3:** no blocking findings and no outstanding findings.

Integrity snapshots matched after every assessment.

## Limitations

- Nothing contacts YouTube. Real extraction, cookies, the Deno runtime against YouTube's player, merging video and audio with ffmpeg, and caption payloads are unverified until T25's authorized end-to-end run.
- Progress totals grow when a video-plus-audio download moves to its audio file, so the percentage can fall back at that point (the boundary's stated behavior).
