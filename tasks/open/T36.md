# T36: Restore transaction exception safety after COMMIT failure

**Priority:** Medium (review F2).

Evidence: [review F2](../../project-review-2026-11-10.md#f2--medium-failed-transaction-finalization-can-poison-a-long-lived-connection), reproduced at `d565907039b7550f550d860f3d4fdd2891ebc8d4`. A temporary SQLite connection authorizer denied exactly one COMMIT; `Store.check()` raised, the connection remained in a transaction, and the next operation failed with `cannot start a transaction within a transaction`. Explicit rollback restored it. This proves missing cleanup, not that all storage errors have that behavior.

Paths: `youtube_collector/store.py`, `tests/test_store.py`, and connection ownership in `api.py`/`worker.py` if a failed connection must be discarded. Outcome: transaction finalization is exception-safe; a failed operation either leaves a usable connection or makes its replacement explicit, preserves the original failure and never acknowledges an uncommitted result. Account for errors that already rolled back automatically and errors during rollback itself. Validation: real temporary SQLite databases with controlled body, COMMIT and cleanup failures; assert transaction state, persisted contents and successful subsequent operations or explicit reconnection; targeted mutation evidence for rollback and acknowledgement invariants. Dependencies: none; automatic job recovery remains [T35](T35.md), not part of this task.
