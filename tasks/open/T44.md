# T44: Report stale or rotated cookies

**Priority:** Medium. Decided by DESIGN C56.

Evidence: source inspection of the locked yt-dlp 2026.10.26 on 2026-11-14, not tried against YouTube. After every request `yt_dlp/extractor/youtube/_base.py` checks whether the login cookies it was given still exist; when they do not, it only calls `report_warning` with "The provided YouTube account cookies are no longer valid. They have likely been rotated in the browser as a security measure…" and continues unauthenticated. A public video then downloads normally, and the collector's `_YtDlpLogger.warning` just logs the line, so stale cookies are silent. Limitation of this signal, from the same source: the warning fires only when yt-dlp found account cookies at the start of an extraction (`_initialize_cookie_auth` sets `_passed_auth_cookies`) and they disappear during it, which is rotation. Cookies that are already expired or logged out when loaded never set that flag, so yt-dlp runs unauthenticated with no warning at all; its only trace is the absence of the debug line "Found YouTube account cookies", which yt-dlp prints in verbose mode only.

Outcome: the yt-dlp adapter recognises that warning and records when it last occurred; `/health` reports it as a warning and logs stay as they are. `/health` also reports the cookie database's modification time, read with `stat` only, as a rough indication of how old the cookies are. Neither changes the 200 or 503 status. The match is a hint that a yt-dlp update can break, like the failure categories, so it lives in one named place with a test tied to the locked yt-dlp's wording: the test should fail when a yt-dlp update changes the message, which is the prompt to update the match.

The user accepted that gap for now (C60): this task detects rotation only, and cookies that are present but carry no login are left to `blocked` failures and the file's age. Revisit after the cookie run under [T25](T25.md) shows whether it matters. Open detail for the executor to state as an assumption: when the warning clears. Proposed: it shows the time of the most recent occurrence and persists until the process restarts, since cookies cannot become valid again without the user refreshing the profile, which already involves stopping the service.

Safety: the modification time is file metadata; the service never opens the database itself, and tests use synthetic files. The warning text may be logged; cookie values never are.

Paths: `youtube_collector/youtube.py`, `youtube_collector/api.py`, `youtube_collector/responses.py`, tests, README, DESIGN 5.11 and 5.14. Compatibility surface: additive `/health` fields only.

Validation: an adapter test that feeds the exact message from the locked yt-dlp source through the logger and observes the recorded state, with an unrelated warning leaving it unset; API tests for the health fields; a check that the cookies-in-use path still works when the modification time cannot be read. Real confirmation that YouTube produces this warning with expired cookies belongs to the cookie run under [T25](T25.md) and needs the user's authorization for that run. Dependencies: [T43](T43.md).
