# T35: Exit the process when the worker cannot continue, so Docker restarts it

**Priority:** High (review F1 of 2026-11-10). Mechanism decided by DESIGN C53 and C59 on 2026-11-14; ready.

**History:** recorded from [review F1](../../project-review-2026-11-10.md#f1--high-persistence-failure-can-strand-work-while-the-worker-looks-healthy) as "automatically recover work stranded by persistence failures" (C48) and deferred on 2026-11-09 (C51), when the options offered were retrying the save in memory or requeueing once the fault clears. On 2026-11-14 the user chose a third option, crash and restart (C53), which supersedes that deferral. The reproduction stands: at `d565907`, an error injected into `finish_item` after publication left the job and item `running`, the next step was idle, and `/health` stayed healthy; an explicit `recover()` restored progress.

Evidence: validated defect, reproduced as above; `Worker.run` in `youtube_collector/worker.py` still logs a failed step and continues. Outcome: any error that escapes `Worker.step`, and anything that ends the worker thread (opening the store, `recover()`, a `BaseException`), ends the process with a non-zero status instead of leaving it serving; Docker's `restart: unless-stopped` starts it again and the existing `Store.recover` requeues the interrupted unit, so a file already published is found `existing`. Item-level failures stay as they are: they are caught, recorded and never crash the process.

Direction, to be revalidated by the executor: the worker takes an injected fatal-error callback, so tests never kill the test process, and the service's composition supplies the one that ends the process. The exit must not depend on a graceful shutdown completing, because the fault that triggers it is typically a broken database and the API's database thread can block without a bound (C50); log the error and flush logging first. Whether to attempt a short graceful shutdown before the hard exit is the executor's assumption to state. Docker restarts on any exit status under `unless-stopped`; confirm that against Compose documentation rather than memory.

Paths: `youtube_collector/worker.py`, `youtube_collector/store.py`, `youtube_collector/api.py`, `youtube_collector/__main__.py`, `tests/test_worker.py`, `tests/test_main.py` with `tests/lifecycle_service.py`, README "Running the service" (the stranded-job paragraph), DESIGN 5.12 (replace its "Planned" note), 5.14 and section 14. Compatibility surface: the database schema version rises, so an existing database file is refused at startup and must be recreated (C44); a capped unit appears as a failed item with a failure record, using existing fields; no setting changes; `threads.worker` in `/health` stays.

Validation: a unit test that a failing step and a failing `recover()` each invoke the fatal callback exactly once and stop the loop; a process-level test in the lifecycle harness that injects one save failure after publication, observes a non-zero exit, restarts on the same database and staging directory, and finds the item `done` with media `existing` and exactly one download recorded; the analogous case for a failure while saving a playlist expansion. Also: tests that the pause precedes the exit, on an injected clock or wait; that a unit interrupted up to the cap is requeued and at the cap is failed with a failure record while a later job still runs; and that an older schema version is refused. Mutation evidence is required for "a unit is never left `running` or `expanding` by a live process", for "no second download after the restart" and for "a unit at the cap is never requeued". Host check for [T10](T10.md): Docker restarts the container after the exit.

Accepted costs to document, from C53: a database that stays broken becomes a restart loop; each restart expands an interrupted playlist again; an item whose published file was moved is downloaded again. Limits on that loop, decided by C59, are part of this task. Docker's restart delay is not a dependable pace: as recalled from Docker's documentation, to be verified by the executor, it starts at 100 ms, doubles to at most a minute and resets once a container has run for 10 seconds, so a unit that takes longer than that to fail would restart almost at once, indefinitely, and each turn can contact YouTube. First, the process pauses for a fixed time before it exits, proposed 60 seconds as an implementation default, which bounds any loop to one attempt per pause; state what the API and `/health` report during the pause. Second, the database counts how often each item, and each playlist expansion, has been interrupted, and once a unit reaches the cap, proposed 3, `recover` records it as failed with a failure record instead of requeueing it, so a unit that crashes the process every time stops and other work proceeds. The counter is a schema change, so `SCHEMA_VERSION` rises and older database files are refused (C44). Accepted with the cap: ordinary restarts count too, so restarting the service three times during one long download fails that item, and the user resubmits. The failure's phase and category for a capped unit are the executor's assumption to state. Non-goals: retrying failed YouTube jobs, in-memory retry of the save, a Docker healthcheck.
