# T49: A scripted, opt-in live canary against real YouTube

**Priority:** Medium. Decided by DESIGN C58.

Evidence: planning step. Updating yt-dlp is this project's routine change, and nothing verifies an update except the manual runs recorded in [T25](T25.md), which were performed by hand and would be performed differently next time. No automated test may contact YouTube, and that stays true.

Outcome: one command that starts the service on loopback, submits a short list of videos or a playlist that the user names for that run, polls to completion, and writes a result record: yt-dlp, Deno and ffmpeg versions, each job's outcomes and failures with raw messages, file names and sizes, a decode check of each MP4, a parse check of each SRT, and the `/health` samples taken during the run. The record is suitable for pasting into a task's completion record and gives [T45](T45.md) verbatim error messages.

Safety, which bounds the whole task ([AGENTS](../../AGENTS.md#safety)): every run needs the user's explicit authorization for that run and those videos; the script has no default targets and refuses to start without them and without an explicit acknowledgement flag; it is not a pytest test, is not collected by the suite and is not part of any gate; by default it uses a throwaway staging directory and database and no cookies; using the real share or a cookie profile requires the REAL DATA container and separate explicit flags. Writing and offline-testing the script authorizes no run, and the executing agent MUST NOT run it against YouTube.

Paths: a new script, README Testing, [T25](T25.md), which can use it for its remaining runs. Compatibility surface: none for the service. Validation: offline tests of the refusal paths and of the record format, run against a fake service or fake adapters; the first live run is the user's, recorded as such. Dependencies: none; more useful after [T43](T43.md) and [T44](T44.md), so a cookie run reports their warnings.
