# T40: Download and merge media in a local scratch directory, then copy it to the share

**Priority:** High. Decided by DESIGN C54.

Evidence: design decision from the 2026-11-14 review, not a defect. Today `Worker._download_media` hands yt-dlp a path inside the `.staging-*` directory on the share, so yt-dlp's separate video and audio files and the ffmpeg merge all run over SMB, and a killed download leaves its partial files on the share, where nothing may remove them because other tools create `.staging-*` directories too.

Outcome: yt-dlp downloads and merges into a scratch directory on container-local storage; the worker then copies the finished file into the stage directory beside its destination and publishes it through `staging.publish` under `NEVER`, exactly as now. The copy is the collector's own chunked loop, so [T42](T42.md) can refresh the staging check from it. A completed `write` to a network share may only have reached the page cache, so decide and state how the copy flushes: without periodic flushing, a stalled share is noticed late and the final close of a large file can itself be a long silent step. The scratch file is removed after publication and after any failure. At startup, before the worker takes work, the service empties the scratch directory.

Direction, to be revalidated: a new setting `COLLECTOR_SCRATCH_DIR`, required like the staging directory or defaulting to a path the image creates; a named volume `collector_scratch` in `docker-compose.yaml`, a matching development volume in `.devcontainer/docker-compose.devcontainer.yaml` (its volume list uses `!override`, so it must be added there explicitly), and the directory created with the runtime user's ownership in the Dockerfile, as the database directory is. The marker is still checked before the item starts and again before publication (5.13). A failed download, a full scratch volume and a failed copy all fail the item with phase `media`; check that `categorize` reports a full scratch volume and a copy failure as `filesystem`.

Safety, which is the high-impact part: emptying the scratch directory deletes files, and DESIGN section 13 says the collector never deletes anything from staging. Startup MUST refuse to run, without deleting anything, when the scratch directory is the staging directory, lies inside it or contains it, or holds the staging marker. Deletion removes only entries inside the configured directory and does not follow symlinks out of it.

Paths: `youtube_collector/worker.py`, `youtube_collector/staging.py` or a small new module for the scratch directory and the copy, `youtube_collector/config.py`, `youtube_collector/api.py`, `docker-compose.yaml`, both devcontainer Compose files if they need the volume, `Dockerfile`, tests, README (configuration table, the `.staging-*` cleanup paragraph), DESIGN 5.4, 5.12, section 7 and section 14. Compatibility surface: one new setting and one new volume; file names, the layout on the share, outcomes and the HTTP API are unchanged.

Validation: worker tests that the media adapter never receives a path under the staging root, that the published file's bytes equal the downloaded ones, that scratch is empty after success and after each failure, and that a marker lost before publication publishes nothing; startup tests for the wipe and for each refusal; a lifecycle test that a process killed mid-download leaves nothing on the share and that the restart removes the scratch leftovers. Mutation evidence is required for "the wipe never deletes outside the scratch directory", "nothing is published when the marker is gone" and "`NEVER` still preserves a competing file". Host checks for [T10](T10.md): the volume exists and is writable by the runtime user in the built image.

Non-goals: captions, which stay staged on the share; resuming partial downloads; scavenging `.staging-*` directories on the share. Until T42 lands, keep the existing download heartbeat working so `/health` does not regress. Dependencies: none; land after [T35](T35.md) to avoid conflicting edits.
