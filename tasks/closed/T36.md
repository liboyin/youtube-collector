# T36: Restore transaction exception safety after COMMIT failure

**Outcome:** Implemented; a failed transaction, including a failed COMMIT or rollback, now leaves a usable or replaced connection, raises the error that ended it and acknowledges nothing. Gates, mutation evidence and review passed with no findings.

Evidence: [review F2](../../project-review-2026-11-10.md#f2--medium-failed-transaction-finalization-can-poison-a-long-lived-connection), reproduced at `d565907039b7550f550d860f3d4fdd2891ebc8d4`. A temporary SQLite connection authorizer denied exactly one COMMIT; `Store.check()` raised, the connection remained in a transaction, and the next operation failed with `cannot start a transaction within a transaction`. Explicit rollback restored it. This proves missing cleanup, not that all storage errors have that behavior.

Paths: `youtube_collector/store.py`, `tests/test_store.py`, and connection ownership in `api.py`/`worker.py` if a failed connection must be discarded. Outcome: transaction finalization is exception-safe; a failed operation either leaves a usable connection or makes its replacement explicit, preserves the original failure and never acknowledges an uncommitted result. Account for errors that already rolled back automatically and errors during rollback itself. Validation: real temporary SQLite databases with controlled body, COMMIT and cleanup failures; assert transaction state, persisted contents and successful subsequent operations or explicit reconnection; targeted mutation evidence for rollback and acknowledgement invariants. Dependencies: none; automatic job recovery remains [T35](../open/T35.md), not part of this task.

## Origin and boundary

Raised by the [2026-11-10 project review](../../project-review-2026-11-10.md#f2--medium-failed-transaction-finalization-can-poison-a-long-lived-connection); revalidated against `store.py` at `abb36ba`, where `_write` runs `COMMIT` outside its rollback block and `_read` runs it in a `finally`.

- **Intent:** DESIGN section 7's one connection per thread, used for one short transaction at a time, stays usable after any failed transaction. A failed COMMIT never acknowledges a result, and the caller sees the original error.
- **Dependencies:** none. [T35](../open/T35.md), deferred by C51, will rely on it.
- **Implementation direction:** `_write` and `_read` share one `_transaction(begin)` context manager, with `COMMIT` inside the guarded region. Cleanup rolls back only when `Connection.in_transaction` says a transaction is still open, because SQLite rolls some failures back itself and a second `ROLLBACK` would then replace the real error. If cleanup itself fails, the error is logged, the connection is closed, which discards its transaction, and the store opens a replacement on its next operation.
- **Decisions within DESIGN's latitude (assumptions):** the replacement is opened lazily rather than inside cleanup, because the database may still be unavailable at that moment and an error there would replace the original one. It lives inside `Store`, so neither `api.py` nor `worker.py` changes. `initialize` keeps its own transaction code: its connection is closed on every path, so it cannot poison anything.
- **Compatibility surface:** no HTTP contract, setting or on-disk layout changes. `Store`'s public methods keep their signatures. A read that fails now rolls back rather than commits, which is equivalent because a read transaction changes nothing.
- **Non-goals:** automatic recovery of stranded work (T35); retrying a failed COMMIT, including `SQLITE_BUSY`; any `/health` change.
- **Validation:** real temporary SQLite databases, with a connection authorizer refusing exactly one COMMIT or ROLLBACK, for body, COMMIT and cleanup failures, on reads and writes. Each asserts the error the caller sees, transaction state, what a separate connection can read, and that the next operation succeeds. Replacement is covered when opening it fails once, and after a transaction SQLite already rolled back.
- **Mutation evidence:** COMMIT outside the guarded region; ROLLBACK attempted with no open transaction; a rollback failure replacing the original error; a failed connection kept instead of replaced; a COMMIT failure swallowed, which would acknowledge an uncommitted result.
- **Done:** gates, adversarial review, closed record. No host check is needed.

## Implementation

`youtube_collector/store.py`: `_write` and `_read` share `_transaction`, with `COMMIT` inside the guarded region. `_end_failed_transaction` rolls back only if `in_transaction` is true and, if that fails, logs, closes the connection and clears it. `_connected` opens the replacement on the next operation, using `_connect`, which `__init__` also uses and which closes the connection on any check failure. `list_failures`, the one query outside a transaction, goes through `_connected` too. `tests/test_store.py` gained ten test functions (eleven cases), most using an authorizer that refuses one COMMIT or ROLLBACK. DESIGN section 7 states the contract.

- **M1:** `COMMIT` moved after the guarded region. The connection stayed `in_transaction`; the next operation raised `cannot start a transaction within a transaction`.
- **M2:** `ROLLBACK` run unconditionally. A connection SQLite had already rolled back was replaced (`assert None is <Connection>`).
- **M3:** cleanup errors not caught. The caller saw `not authorized` instead of the body's `ValueError`.
- **M4:** the failed connection kept. `cannot start a transaction within a transaction`.
- **M5:** the re-raise dropped, so a failed COMMIT was acknowledged. `DID NOT RAISE DatabaseError`.
- **M6:** the closed connection left in place. `Cannot operate on a closed database`.
- **M7:** the discarded connection not closed. `database is locked` after the 30-second busy timeout.
- **M8:** `list_failures` using the discarded connection. `'NoneType' object has no attribute 'execute'`.
- **M9:** `COMMIT` in a `finally`, as before this change. `cannot commit - no transaction is active`. The reviewer noted that this failure does not isolate read cleanup and added a targeted read commit-on-error mutant, which its run also killed.

The runs passed `--show-capture=no` because `mutate.py` reads a captured log line beginning `ERROR` as a pytest error and would otherwise label a real kill invalid.

## Limitations

The authorizer refuses a statement before SQLite runs it. Real storage failures, whose COMMIT can fail part-way or roll back by itself, were not injected; the `in_transaction` check is what handles them, and the case where SQLite has already rolled back is exercised by a body issuing `ROLLBACK` itself. [T35](../open/T35.md) remains deferred, so a stranded unit still needs a restart even though the connection is now usable.
