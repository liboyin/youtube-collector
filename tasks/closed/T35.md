# T35: Exit the process when the worker cannot continue, so Docker restarts it

**Outcome:** Done. A failed worker ends the process with status 1 after a 60-second pause, and recovery fails a unit at its third interruption.

**History:** recorded from [review F1](../../project-reviews.md#f1--high-persistence-failure-can-strand-work-while-the-worker-looks-healthy) as "automatically recover work stranded by persistence failures" (C48) and deferred on 2026-11-09 (C51), when the options offered were retrying the save in memory or requeueing once the fault clears. On 2026-11-14 the user chose a third option, crash and restart (C53), which supersedes that deferral. The reproduction stands: at `d565907`, an error injected into `finish_item` after publication left the job and item `running`, the next step was idle, and `/health` stayed healthy. An explicit `recover()` restored progress.

Evidence: validated defect, reproduced as above; `Worker.run` in `youtube_collector/worker.py` still logs a failed step and continues. Outcome: any error that escapes `Worker.step`, and anything that ends the worker thread (opening the store, `recover()`, a `BaseException`), ends the process with a non-zero status instead of leaving it serving; Docker's `restart: unless-stopped` starts it again and the existing `Store.recover` requeues the interrupted unit, so a file already published is found `existing`. Item-level failures stay as they are: they are caught, recorded and never crash the process.

Direction, to be revalidated by the executor: the worker takes an injected fatal-error callback, so tests never kill the test process, and the service's composition supplies the one that ends the process. The exit must not depend on a graceful shutdown completing, because the fault that triggers it is typically a broken database and the API's database thread can block without a bound (C50); log the error and flush logging first. Whether to attempt a short graceful shutdown before the hard exit is the executor's assumption to state. Docker restarts on any exit status under `unless-stopped`; confirm that against Compose documentation rather than memory.

Paths: `youtube_collector/worker.py`, `youtube_collector/store.py`, `youtube_collector/api.py`, `youtube_collector/__main__.py`, `tests/test_worker.py`, `tests/test_main.py` with `tests/lifecycle_service.py`, README "Running the service" (the stranded-job paragraph), DESIGN 5.12 (replace its "Planned" note), 5.14 and section 14. Compatibility surface: the database schema version rises, so an existing database file is refused at startup and must be recreated (C44); a capped unit appears as a failed item with a failure record, using existing fields; no setting changes; `threads.worker` in `/health` stays.

Validation:

- A unit test that a failing step and a failing `recover()` each invoke the fatal callback exactly once and stop the loop.
- A process-level test in the lifecycle harness that injects one save failure after publication and observes a non-zero exit. It restarts on the same database and staging directory, and finds the item `done` with media `existing` and exactly one download recorded.
- The analogous case for a failure while saving a playlist expansion.
- Tests that the pause precedes the exit, on an injected clock or wait.
- Tests that a unit interrupted up to the cap is requeued, and at the cap is failed with a failure record while a later job still runs.
- A test that an older schema version is refused.

Mutation evidence is required for "a unit is never left `running` or `expanding` by a live process", for "no second download after the restart" and for "a unit at the cap is never requeued". Host check for [T10](../open/T10.md): Docker restarts the container after the exit.

Accepted costs to document, from C53:

- A database that stays broken becomes a restart loop.
- Each restart expands an interrupted playlist again.
- An item whose published file was moved is downloaded again.

Limits on that loop, decided by C59, are part of this task. Docker's restart delay is not a dependable pace. As recalled from Docker's documentation, to be verified by the executor, it starts at 100 ms, doubles to at most a minute and resets once a container has run for 10 seconds. A unit that takes longer than that to fail would therefore restart almost at once, indefinitely, and each turn can contact YouTube.

- First, the process pauses for a fixed time before it exits, proposed 60 seconds as an implementation default, which bounds any loop to one attempt per pause. State what the API and `/health` report during the pause.
- Second, the database counts how often each item, and each playlist expansion, has been interrupted. Once a unit reaches the cap, proposed 3, `recover` records it as failed with a failure record instead of requeueing it. A unit that crashes the process every time then stops, and other work proceeds.
- The counter is a schema change, so `SCHEMA_VERSION` rises and older database files are refused (C44).
- Accepted with the cap: ordinary restarts count too, so restarting the service three times during one long download fails that item, and the user resubmits.
- The failure's phase and category for a capped unit are the executor's assumption to state.

Non-goals: retrying failed YouTube jobs, in-memory retry of the save, a Docker healthcheck. Dependencies: [T36](T36.md), done. Independent of T40–T44, but T40–T42 also rewrite parts of `worker.py`, so land this first.

## Origin and boundary

Accepted for implementation by the user on 2026-11-17, as the first task of the recommended order and the first group run under the consolidated governance. It is a group of one task, committed as one change.

- **Intent:** carry out C53 and C59 (DESIGN 5.12). An error that escapes the worker's handling of a unit, or that ends the worker's run, ends the process with status 1 after a fixed pause. Restart recovery counts each unit's interruptions and fails a unit at the cap instead of requeueing it.
- **Dependencies:** C44, C50, C53 and C59, and T36, which is done. Docker's documentation, read on 2026-11-17, confirms the restart premise. Compose says `unless-stopped` "restarts the container irrespective of the exit code". The `docker container run` reference gives the delay: 100 ms, doubled up to 1 minute, reset after 10 seconds of running.
- **Implementation direction:**
  - `Worker` takes a required `on_fatal` callback and loses `error_wait`. `run` catches any `BaseException` from opening the store, `recover()`, a step or `on_stopped`. It marks itself failed, logs the error and calls `on_fatal` once. `on_stopped` still runs first.
  - `api._Runtime` supplies `on_fatal`. It logs, sleeps for `Settings.fatal_pause`, flushes the log handlers and the standard streams, and calls `os._exit(1)`. `Components` gains `sleep` and `exit_process`, so that tests inject both.
  - `store` adds an `interruptions` column to `jobs` and `items` and raises `SCHEMA_VERSION` to 3. `recover()` increments the counter of each running item and each expanding job. Below `MAX_INTERRUPTIONS` it requeues the unit. At the cap it fails the unit with a failure record, and finishes the job if no unit of it remains.
- **Decisions within DESIGN's latitude (assumptions):**
  - No graceful shutdown before the hard exit. The fault is usually a broken database, and the API's database thread can block without a bound (C50). A partial download cannot be in progress, because the worker's step has already ended.
  - The pause runs on the worker thread, after the worker has released its adapters. The thread is a daemon, so a SIGTERM during the pause still ends the process through the normal shutdown.
  - During the pause the API serves as usual, and submissions are queued for after the restart. `/health` answers 503 with `threads.worker` false, because the worker has failed even though its thread still exists.
  - The pause is 60 seconds and the cap is 3, as C59 proposes. Both are implementation defaults, not environment settings. `fatal_pause` follows `staging_health_max_age`, which is a `Settings` field without a variable.
  - A capped item fails in its job's primary phase: `media` when the job wants media, otherwise `captions`. A capped expansion fails in phase `expanding`. Both use category `internal` and a message that names the count. The item's outcomes stay null, because the interruption left them unknown.
  - The exit status is 1.
- **Compatibility surface:**
  - The schema version rises to 3, so a version 2 database is refused at startup and must be recreated (C44).
  - A capped unit uses existing fields: a failed item or a finished job, with a failure record.
  - `threads.worker` in `/health` stays, and is also false while a failed worker pauses before the exit.
  - No setting, endpoint or file name changes.
- **Non-goals:** retrying failed YouTube jobs, an in-memory retry of the save and a Docker healthcheck. Also no removal of stage directories left by a crash (C46), and no graceful shutdown before the exit.
- **Validation:**

  - API unit tests: the log precedes the pause, the pause precedes `exit_process(1)`, and `/health` reports the failed worker during the pause.
  - Store tests: a unit is requeued below the cap, and failed at the cap with its failure record. A later job still runs. A version 2 database is refused.
  - Lifecycle process tests: one injected save failure after publication gives exit status 1. A restart on the same database and staging directory then finds the item `done` with media `existing` and exactly one download. The same holds for one injected failure while saving a playlist expansion: two expansions, then the item downloads.

## Implementation

- `Worker` takes a required `on_fatal` callback and exposes `failed`. `run` sends any `BaseException` from opening the store, `recover()`, a step or `on_stopped` to `on_fatal` exactly once, after `on_stopped`. The `error_wait` retry is gone.
- `api._Runtime._fatal` logs the error, sleeps `Settings.fatal_pause`, flushes the log handlers and standard streams, and calls `exit_process(1)`. `Components.sleep` and `Components.exit_process` default to `time.sleep` and `os._exit`.
- `/health` reports `threads.worker` false once the worker has failed, also while its thread pauses before the exit.
- `store` raises `SCHEMA_VERSION` to 3 and adds `interruptions` to `jobs` and `items`. `recover()` requeues a unit below `MAX_INTERRUPTIONS` (3) and fails it at the cap with an `internal` failure record. A job with no unit left finishes. `finish_item` and `recover()` share `_finish_job_if_done`.
- The lifecycle harness gains `fail-save`, `fail-expansion-save`, a one-entry fake playlist and a 0.2-second fatal pause.
- API tests now build their components with a refused process exit and a no-op pause, so that no test can end the pytest process.
- DESIGN 5.12, 5.14, section 7, section 12 and section 14, README "When the worker fails", TODO and [T10](../open/T10.md) are updated.

## Review

Independent reviewer: Codex CLI session `01a1e797-f7b4-72f2-9980-46f44609af17`, dispatched through the shared `dispatch.py` as `gpt-6.1-sol` with medium effort. Those values are dispatch settings, which the reviewer cannot observe. The reviewer read the full diff, checked the supplied gates and reran all seven mutants: the 13 baseline cases passed and every mutant was killed.

First verdict: **1 blocking finding.**

- **Blocking:** `_Runtime._fatal` flushed the log handlers and the standard streams without protection before `exit_process(1)`. A failing flush, such as `BrokenPipeError` from a closed stream, ended the worker thread without the exit. The API then stayed alive without a worker, so Docker would never restart it. The reviewer reproduced it with three focused probes.
  - Main-agent validation: **Validated**, from the code. Logging calls swallow their handlers' errors, but `flush()` does not.
  - Disposition: **Fixed.** Each flush is now best effort, and a `finally` runs the exit whatever the pause or the diagnostics raise. `test_the_fatal_exit_happens_even_if_its_diagnostics_fail` covers a failing handler, stdout, stderr and pause. M8 and M9 are its mutation evidence.

Integrity snapshots before and after the first assessment matched.

Follow-up verdict from the same session: **No blocking findings.** The earlier finding is resolved, and there are no new findings. The reviewer reran the ten focused cases, including its three reproductions and both restart lifecycle tests, and reran M8 and M9. Both mutants were killed, with provenance verified and no surviving threads. The follow-up snapshots matched.
