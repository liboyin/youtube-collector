# T32: Name files with the ID first

**Outcome:** Implemented; files and playlist folders are named with the ID first, and mutation evidence and review passed after fixing one review finding.

Name published files and playlist folders `<id> - <title>`, as decision C45 requires. Evidence: `staging.py` builds and matches `Title [id].ext`.

## Origin and boundary

Planned from DESIGN decisions C44 and C45, which the user made on 2026-11-08 after describing the two workflows in DESIGN section 3.

- **Intent:** DESIGN 5.1 and 5.4: media and captions are `<videoID> - <Title>.<ext>`, playlist folders `<playlistID> - <Playlist title>/`, and an existing artifact is recognized by its `<videoID> - ` prefix and suffix.
- **Dependencies:** C23, C33 and C44, C45. Independent of [T33](T33.md), which touches the same test files and so runs after it.
- **Implementation direction:** in `youtube_collector/staging.py`, replace the ` [id]` tag with a `<id> - ` prefix built from the same reserved-character replacement. `build_filename` has no prefix option, so the prefix's bytes come off its `max_length`; only the title is truncated and the name still fits in 220 bytes. `find_artifacts` matches `startswith(prefix)` and `endswith(suffix)`, literally. `playlist_dir_name` strips trailing dots and spaces from the finished name, because a folder name now ends with free text rather than `]`. `captions_name_for` keeps pairing by the existing MP4's stem.
- **Decisions within DESIGN's latitude (assumptions):** trailing dots and spaces are stripped only from folder names, because a file name always ends in its suffix. A title of exactly `.` or `..` still fails the item, through `build_filename`, as "nothing left to keep" (5.4). A name's empty title part still counts when found on disk: `<id> - .mp4` is matched like any other title.
- **Compatibility surface:** the on-disk layout of the staging area and the paths in API responses change format. There is deliberately no compatibility with `Title [id].ext` (C44): such files are not recognized. HTTP endpoints, settings and the database are unaffected.
- **Non-goals:** recognizing or migrating old names; changing what counts as existing (C23, C33); any lifecycle change (T33).
- **Validation:** `tests/test_staging.py` covers the names, truncation of multi-byte titles to 220 bytes with the prefix whole, an ID too long to leave room, literal matching of glob characters, rejection of old-format names and of an ID that is only a prefix of another, and folder names losing trailing dots and spaces. `tests/test_worker.py` and `tests/test_api.py` assert the new paths end to end.
- **Mutation evidence:** existing-artifact recognition protects against duplicate downloads and overwrites, so: the prefix check dropped, the separator dropped from the prefix (an ID matching a longer ID's files), the suffix check dropped, the prefix's bytes not taken off the limit, and the trailing strip removed.
- **Done:** gates, adversarial review, closed record. No host checks.

## Implementation

- **`youtube_collector/staging.py`:** `_id_prefix` replaces `_id_tag`, and `_prefixed_name` takes the prefix's bytes off `build_filename`'s limit. `find_artifacts` matches the prefix and the suffix literally. `playlist_dir_name` removes trailing dots and spaces and raises `ValueError` when no title character is left.
- **Tests:** `tests/test_staging.py` is rewritten for the new names; `tests/test_worker.py` and `tests/test_api.py` assert the new paths.

`pathlib-extensions` needed no change: `build_filename` truncates the title and the prefix is prepended here. No README or DESIGN section 14 text named the old format.

## Limitations

- Trailing dots and spaces are removed because SMB shares do not accept them; this was not tried against the real share.
- Files named `Title [id].ext` are not recognized, so a video already in staging under that name is downloaded again (C44).
