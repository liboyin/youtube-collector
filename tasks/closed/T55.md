# T55: Check the documentation with a tool

**Outcome:** Implemented. `check_docs.py` checks links, task files and style, and AGENTS.md requires it for every change that touches a Markdown file. The gates and the adversarial review passed, after three Blocking findings and one Non-blocking finding were fixed.

Replace manual checks of the documentation with a tool. Evidence: validated by reading the task rules on 2026-11-14. The rules asked the agent to check by hand that the links of a moved record resolve, and that the TODO index matches `open/`. Agents also checked the rules of [STYLE.md](../../STYLE.md) by hand after each rewrite. [AGENTS.md](../../AGENTS.md#governance-files) says that a tool is the first home for such a rule.

## Origin and boundary

The user accepted this task on 2026-11-15 and decided two points. The tool checks whole files, except the files that are not rewritten as a whole, where it checks changed lines only. A rule in AGENTS.md triggers the tool for every change to documentation, like the gates for code. The check is cheap: a prototype took 0.04 seconds for all Markdown files.

- **Intent:** a new script, `check_docs.py` in the repository root, exits with 0 only if the documentation passes three groups of checks:
  - **Links:** each relative link in a Markdown file resolves, and each anchor exists in its target file.
  - **Tasks:** each file in `tasks/open/` has one line in the index of [TODO.md](../TODO.md), and each index line has a file. No ID is both open and closed. The title of a task file starts with the ID in its file name.
  - **Style:** the rules of STYLE.md that a tool can check. These are the sentence limits, semicolons, alternatives joined by a slash, the paragraph limit and one source line for each paragraph.
- **Dependencies:** none.
- **Implementation direction:** a standalone Python script with no imports from the application. It lists the Markdown files with `git ls-files` and reads changed lines from `git diff HEAD`. Tests go in `tests/tooling/test_check_docs.py` and use owned Git repositories.
- **Decisions within DESIGN's latitude (assumptions):**
  1. The check for changed lines only applies to `DESIGN.md`, `project-review-2026-11-10.md`, `tasks/open/` and `tasks/closed/`. STYLE.md names the first two and the completion records. The open task files are added because they are rewritten only when a task is bounded.
  2. A changed line is a line that `git diff HEAD` adds, with rename detection, or any line of an untracked file. A record that `git mv` moved therefore keeps its old lines unchecked.
  3. The tool cannot tell an instruction from a description. It applies the limit of 28 words to list items and the limit of 35 words to other prose.
  4. Code blocks, inline code, tables, headings, block quotes and YAML front matter are exempt from the style checks. Link checks skip code blocks and inline code.
  5. The link check covers every Markdown file, including the completion records. All of their links resolve today.
- **Compatibility surface:** none for the service. The repository gains one script and one required check for documentation changes.
- **Non-goals:** a git hook. A test in the suite that runs the tool on this repository: the documentation check stays separate from the code gates. A check of the rules that need judgment, such as the active voice or one term for one concept.
- **Validation:** a test for each rule, with a failing input and a passing input in an owned repository. Tests for each exemption, for the changed-lines mode with a modified file, a moved file and an untracked file, and for the exit codes. The tool passes on this repository. The three gates.
- **Mutation evidence:** none is required. The tool protects no high-impact invariant.
- **Done:** gates, adversarial review, closed record. The same change deletes the prose that the tool replaces in [tasks/README.md](../README.md), and adds the rule to AGENTS.md. The user reviews those governance edits. No host check is needed.

## Implementation

- `check_docs.py`, in the repository root:
  - `markdown_files` lists the tracked files and the untracked files that are not ignored. `changed_lines` reads the added lines from `git diff HEAD` with rename detection.
  - `classify` gives each line a kind: a list item, other prose, a line with links but no style rules, or a skipped line.
  - `check_links` checks inline links, link definitions and references to a definition. `anchors` derives the anchors of a file from its headings.
  - `check_tasks` compares the task files with the index in `tasks/TODO.md`.
  - `check_style` and `line_problems` apply the style rules to the lines in scope.
  - The exit status is 0 for no problem, 1 for at least one problem and 2 if the check cannot run.
- `tests/tooling/test_check_docs.py`: 59 tests in owned Git repositories.
- Documentation, reviewed by the user:
  - AGENTS.md requires the check under Validation and Review.
  - README Testing describes the check.
  - STYLE.md names the tool in its Scope section. Its slash example is now in a code span, because the tool reported it.
  - tasks/README.md loses the manual link check and the manual index check. It keeps the manual check of dependencies between tasks.

## Review

Reviewer: an independent Codex CLI session started by `dispatch.py`, session `01a1ddda-22cb-73e3-99d3-66b4130cc668`. The dispatch arguments were model `gpt-6.1-sol` and effort `medium`. The target was the frozen worktree. The integrity snapshots before and after each assessment were identical.

First assessment: three Blocking findings and one Non-blocking finding. The reviewer ran the 42 tests of that candidate and five probes of its own through `mutate.py --tests`.

1. **Blocking, validated, fixed.** The link pattern missed a link with a title and a reference link, so broken ones passed. It also rejected an existing destination with balanced parentheses. Fix: the pattern handles titles, angle brackets and one level of parentheses. Link definitions are checked, and a reference without a definition is reported.
2. **Blocking, validated, fixed.** A colon counted as the end of a sentence, so a sentence of 40 words with a colon in the middle passed. Fix: a sentence ends only at a full stop, a question mark or an exclamation mark, also inside closing markup. While testing the fix, the main agent found a second defect. The removal of the list marker was not anchored, and it could delete marker-like text inside a line. It is now anchored.
3. **Blocking, validated, fixed.** Any fence toggled the code state, so a block of four tildes that held backtick fences was read as prose. Fix: a block ends only at a fence of the opening character, at least as long, with nothing after it.
4. **Non-blocking, validated, fixed.** The section that this change deleted from tasks/README.md also held a check of dependency consistency, which the tool does not perform. The section is restored with that one manual check.

Follow-up on the refrozen candidate, same session: **no blocking findings, and all four findings resolved.** The reviewer ran the 59 tests and its five original probes in a scratch copy: 64 passed with verified provenance. It accepted the full gates from the supplied results.

## Limitations

- The tool applies the limit of 28 words to list items and the limit of 35 words to other prose. It cannot tell an instruction from a description.
- An abbreviation with a full stop, such as "e.g.", ends a sentence for the tool. The tool then counts two short sentences, so it errs toward a pass.
- A destination with more than one level of nested parentheses is not recognized as a link.
- A file that is moved and changed by more than 80% counts as new, and the tool then checks all of its lines.
- This record was completed after the last assessment, so the committed record differs from the reviewed task file. The script, the tests and the other documentation files are identical to the reviewed files.
