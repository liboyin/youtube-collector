# T21: Worker thread

**Outcome:** Implemented; mutation evidence and review passed.

## Origin and boundary

Planned by [T9](T9.md). The accepted boundary, as it stood in TODO:

- **Intent:** DESIGN 5.3, 5.4, 5.7, 5.9, 5.10's throttling, 5.12 and 5.13, with C9 and C36: the single thread that talks to YouTube, composing T15–T20.
- **Implementation direction:** `youtube_collector/worker.py`, class `Worker`, with the adapters behind `MediaSource` and `CaptionSource` protocols. `step(store)` takes at most one unit and returns `PAUSED`, `IDLE`, `EXPANDED` or `PROCESSED`; tests drive it directly. `run()` opens the thread's own store, calls `recover()` (DESIGN 5.12), then loops over `step` with waits that `wake()` (after a submission) and `stop()` cut short.
  - **Scheduling:** `next_work` with the cursor the worker keeps (C9). An expansion counts as one unit.
  - **Pausing:** while the marker is missing, `step` changes no record and returns `PAUSED`; the pause and the resume are each logged once (DESIGN 5.13).
  - **Items:**
    - The destination is the staging root, or the playlist folder named from the expanded title. `NEVER` is checked per artifact before any network work: existing MP4s are looked up for every kind, so new captions pair with a single MP4 (C33), and existing SRTs for kinds that want captions.
    - A metadata request happens only when media must be downloaded, or captions need a title that no single MP4 or listed title supplies.
    - Media is downloaded into a stage and published. If it fails, captions are not attempted and the item fails.
    - Captions: no track gives `unavailable`. A caption-service error (any `youtube-transcript-api` exception or `requests` exception) gives `error` plus a failure in `videos-with-captions` items, and fails `captions` items. Any other caption error fails the item.
    - The outcome, paths, track and failures are written in one `finish_item` call, which applies supersession.
  - **Progress:** written at most once per `progress_interval` (default 1 s) per item, on an injected monotonic clock.
  - **Notification:** an injected `notify` callback runs after every store write; T23 supplies the thread-safe notifier.
  - **Shutdown:** `stop()` stops the loop taking units, and the current unit finishes (C36). The composition root (T24) joins the thread within the grace period and otherwise abandons it to restart recovery.
- **Decisions within DESIGN's latitude (assumptions):**
  - Media takes its name from the metadata title, which is the current title; a playlist's listed title names captions only when no metadata request is needed (DESIGN 13 allows listing values).
  - The marker is checked again after each file is staged and before it is published, so a share lost mid-download publishes nothing and fails the item as `filesystem` (DESIGN 5.13 requires the check before each item; this narrows the window).
  - A failure while listing the destination fails the item in the phase of its primary artifact (media, or captions for `captions` jobs).
  - An unexpected error from a whole step, such as a database error, is logged and retried after `error_wait`, so the thread survives; an item it interrupted stays `running` until restart recovery.
- **Compatibility surface:** the on-disk layout of DESIGN 5.4 (names, folders, pairing) and the records' outcome fields, as T19 and T24 expose them.
- **Non-goals:** the reconciliation thread (T22), notifier internals (T23), thread start-up, signal handling and the grace period (T24).
- **Validation:** tests with the real store and staging layer under `tmp_path` and fake adapters, covering:
  - every outcome row of DESIGN 5.7, existing artifacts, C33 pairing, playlist folders recreated between items, competing files, a marker lost mid-download or before captions, and progress throttling;
  - round-robin order, and pausing with no record change;
  - recovery and stop through `run`, a failing step, and wake-ups.
- **Mutation evidence:** for acknowledgement (failed items recorded), failure isolation, `NEVER` before network work, the marker checks, caption-error handling by kind, throttling, the cursor and recovery.
- **Done:** gates, review and a completion record.

## Implementation

`youtube_collector/worker.py`: `Worker`, the `MediaSource`, `CaptionSource` and `Track` protocols, `Step`, and `StagingUnavailable` (an `OSError`, so a lost marker is categorized `filesystem`). An internal `_ItemFailed` carries the phase and categorized failure, and `_Outcome` assembles the `ItemResult`. The marker re-check runs inside each publication's write callback, after the file is staged, so raising there discards the stage. DESIGN section 14 lists the module. `tests/test_worker.py` has 36 tests, using the real store and staging layer under `tmp_path` with fake adapters and a fake monotonic clock.

Corrections made during implementation:

- A `captions` job first looked for existing MP4s only when the job wanted media, which broke C33's pairing; MP4s are now looked up for every kind.
- The marker re-check first ran before the download instead of after it, so a share lost mid-download was still published; the test caught it.

## Mutation evidence

The main agent was the primary producer, with the same isolation, command and provenance check as [T15](T15.md#mutation-evidence), on `tests/test_worker.py` (baseline 36 passed). Every mutant was killed:

- **M1, media failure still attempts captions:** `media_failure_fails_the_item_and_skips_captions`, `failure_of_one_item_does_not_stop_the_rest` and `a_marker_lost_during_download_publishes_nothing` failed.
- **M2, a caption-service error fails a `videos-with-captions` item:** the three `caption_service_error_after_media_leaves_the_item_done` cases failed.
- **M3 and M4, no marker re-check before the media or the captions publication:** the matching marker-lost test failed.
- **M5, work starts without the marker:** `step_pauses_without_the_marker_and_changes_nothing` and `run_waits_while_paused` failed.
- **M6 and M7, existing media downloaded or existing captions fetched again:** `existing_media_is_not_downloaded_again` (and `new_captions_keep_the_existing_mp4_stem`) and `existing_captions_are_not_fetched_again` failed.
- **M8, progress not throttled:** `progress_writes_are_throttled` failed.
- **M9, failed items never acknowledged:** 11 tests failed.
- **M10, the round-robin cursor not advanced:** `round_robin_alternates_between_jobs` failed.
- **M11, no recovery at start:** `run_recovers_processes_and_stops` failed. Its `finally` stopped and joined the worker even then.
- **M12, captions not paired with an existing MP4 in `captions` jobs:** `captions_job_pairs_with_an_existing_mp4_without_metadata` failed.
- **M13, a caption-service error in a `captions` job counted as `unavailable`:** `caption_service_error_fails_a_captions_item` failed.

## Review

Codex `gpt-6.1-sol`, medium effort (dispatch arguments), thread `01a1b6a9-0c53-78f1-bda3-7a4ec7e49324`, on the worktree's dirty tree. The reviewer replayed all 13 mutants with verified scratch imports and added four passing probes (seed 210021):

- recovery reuses already published media;
- several MP4 matches make captions use the current title;
- an empty expansion finishes and supersedes an earlier failure;
- stopping acknowledges the current unit and leaves the next queued.

It also ran one more mutant, which ignores `stop`; the last probe killed it. Integrity snapshots matched. Verdict: no blocking findings, no Non-blocking findings or Nits.

## Limitations

- A database error during a step leaves the item it interrupted `running` until the next restart; the boundary accepts this.
- Fake adapters stand in for yt-dlp and the caption service; T25's end-to-end run exercises the composition against YouTube.
